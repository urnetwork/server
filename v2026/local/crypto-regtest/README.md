# Crypto regtest harness

Runs the crypto payment rail's wallet-daemon clients (`controller/crypto_pay_monero.go`,
`controller/crypto_pay_zcash.go`) against the real daemons on private regtest chains, in Docker:

| Container | What |
|---|---|
| `crypto-regtest-monerod` | monerod v0.18.5.4, `--regtest --offline --fixed-difficulty 1` |
| `crypto-regtest-monero-funder` | a spending monero-wallet-rpc; up.sh mines to it |
| `crypto-regtest-monero-view` | the wallet under test: view-only, made with `generate_from_keys` from a separate test wallet |
| `crypto-regtest-zebrad` | zebrad 6.4.2, regtest (mmm/ZCASH-WALLET-DAEMONS.md §A.6), mining to the Zcash funder |
| `crypto-regtest-zecd-funder` | a spending zecd 0.8.2 with the transparent pool on; shields its coinbase |
| `crypto-regtest-zecd-view` | the wallet under test: watch-only zecd from a separate test wallet's UFVK |
| `crypto-regtest-postgres`, `crypto-regtest-redis` | `up.sh --db` only: the end-to-end test's own database (native arm64, tmpfs) |

The binaries are the pinned production releases (xops `host_files/snow/crypto-pay/vars.yml`),
downloaded by `fetch.sh` into `.cache/` and refused unless their sha256 matches the pin. They are
x86_64 builds, run in `linux/amd64` containers (`debian:trixie-20261005-slim`) under Docker
Desktop's emulation. Every container, volume and the network is named `crypto-regtest-*`; ports
are published on 127.0.0.1 only (28881-28883 Monero, 28891-28893 Zcash, 28832/28879 the `--db`
PostgreSQL/Redis; `CRYPTO_REGTEST_PORT_*` in `lib.sh` override them).

## Use

```sh
cd server/local/crypto-regtest
./up.sh --db            # about 3 minutes; writes .state/harness.json (--db: see stage 2)

# stage 1: the clients against the daemons (no database)
cd ../..                # server/
URNETWORK_CRYPTO_REGTEST=1 go test -tags crypto_regtest -count=1 -v -timeout 60m \
    -run 'TestCryptoRegtest(Monero|Zcash)$' ./controller/

# stage 2: pool refill, invoices, payments and the scanner end to end, on the test database.
# With up.sh --db, against the harness's own PostgreSQL and Redis (crypto-regtest-postgres,
# crypto-regtest-redis, tmpfs) through test-env.sh's private portable mode:
source local/crypto-regtest/.state/test-env-portable.sh
# ...or, with the shared stack (local/run-local.sh) up instead:
#   unset WARP_HOME WARP_VAULT_HOME WARP_CONFIG_HOME URNETWORK_TEST_REAL_VAULT
source ./test-env.sh
URNETWORK_CRYPTO_REGTEST=1 go test -tags crypto_regtest -count=1 -v -timeout 60m \
    -run 'TestCryptoRegtestEndToEnd$' ./controller/

cd local/crypto-regtest
./down.sh               # removes the containers, volumes, network and .state/
./down.sh --purge-cache # ...and the downloads
```

`./up.sh --db` on a harness that is already up adds just the database. The portable root
(`.state/portable`, mode 700) holds the server's synthetic vault (`local/testdata/vault`) with the
two services' authorities, and the small files of the config repository beside the server
(`../config`: `pro.yml`, `local/*.yml`, `local/mmdb`), never its data sets.

The tests run against whatever state the chains are in, so they can be repeated without a new
`up.sh`. Run stage 2 after stage 1, not beside it: `TestCryptoRegtestMonero`'s last two steps
kill and restart the view-only wallet-rpc.

## Keys and secrets

Everything is generated by `up.sh` for these chains only, into `.state/secrets/` (0600, gitignored):
RPC logins, wallet passwords, the Monero test wallet's view key, the Zcash test wallet's UFVK, and
the funders' and test wallets' mnemonics (files named `*REGTEST-ONLY*` or `zecd-funder.mnemonic`).
No script prints them, and `down.sh` deletes them.

## Where this differs from production

- **monero-wallet-rpc gets `--allow-mismatched-daemon-version`.** Regtest switches to the newest
  hard fork at height 1, and a wallet without a network flag checks the daemon against mainnet's
  schedule ("Unexpected hard fork version v16 at height …"). Monero's own functional tests pass
  the same flag. Otherwise the view-only wallet runs as on snow (xops
  `crypto-pay-wallet.service.j2`): `--wallet-file`, `--password-file`, digest login from
  `$RPC_LOGIN`, `--trusted-daemon`, `--no-initial-sync`, never `--restricted-rpc`.
- **Monero regtest uses mainnet's address prefixes**, so the tests configure xmr as `mainnet`.
- **Zebra's cookie auth is off** and its RPC listens on the compose network, as in zecd's own
  regtest harness. zecd dials it as `zebra://zebrad:18232` (an RFC 1918 address, so
  `rfc1918_is_local` stays true), where production dials loopback with a copied cookie.
- **zecd polls every 2 s** (`[sync] interval_secs`) instead of 20 s. The watch-only zecd otherwise
  uses production's pools, receivers and `allowed_methods` (`config/zecd-view.toml`).
- **The zcash client has no regtest network** (it knows chains `main`/`test` and prefixes
  `u1`/`utest1`; zecd on regtest says `regtest` and `uregtest1`). Until it has one, the test
  configures zec as `testnet` and puts a shim between the client and zecd that rewrites exactly
  those two things (`cryptoRegtestZecdShim` in `controller/crypto_pay_regtest_test.go`). The test
  uses the real network when `zcashChainName("regtest")` answers `regtest`.
- **zebrad's `estimatedheight` is meaningless on regtest**: the blocks keep the 2011 genesis time,
  and zebrad extrapolates from the tip's time to now (about 6.6 million). The client takes it as
  the network height, so the end-to-end test leaves `node_rpc_url` out of zcash.yml; the lag check
  then compares zecd's scanned height with its view of Zebra's tip.

## Trouble

- A Docker engine restart stops every container: `./down.sh && ./up.sh`.
- `.state/up.log` has compose's and the one-shot daemons' output (no secrets).
- `up.sh` refuses to run over leftovers of an earlier run; `./down.sh` first.
