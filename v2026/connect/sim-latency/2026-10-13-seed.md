# sim-latency research seed: main, 2026-08-13 through 2026-10-13

This is a competitor-facing map of the major architecture, performance, and correctness changes around the measured latency path. It is prepared for the owner's planned end-of-week freeze of main as a new competition epoch: historical examples of successful approaches, supporting correctness work, and instructive tradeoffs that can seed further research. It is not a proposed patch, a new benchmark result, or a source freeze; no source lock or competition policy was changed for this document.

## Executive summary and priorities

Read this first as a **Connect data-plane history**, with SDK integration and server infrastructure supporting it. The most extensive packet-path work is in Connect: preserve already-available bursts across admission, encoding, routing, and socket writes; keep unrelated flows progressing; deliver ACK/control feedback without unnecessary queues; recover the correct retained bytes; and limit the memory owned by every stage. SDK changes determine whether those mechanisms are actually selected, whether native packet batches reach them, and whether a simulated device has independent budgets and a joined lifetime.

Batching is a central example, not a synonym for H1+. An IP burst, an exact-flow admission group, several application frames in one Transfer Pack, several carrier messages in one physical write, and compressed ACK feedback have different identities and limits. August's work made H1-specific groups larger without weakening conservative mixed/H3 bounds, reduced ACK/packet allocation churn, and retained per-item completion. September and October tightened recovery, memory, deadline, and custody invariants; October 10 gave unrelated native-batch groups a ready-first offer before waiting on a blocked group. Some lower-layer batching is directly exercised by the simulator even though its upload bridge still submits each Tun packet separately.

The server-side examples remain important supporting work: resident authorization moved from enumerating SQL inventory to bounded existence/coalescing on October 5, then to deadline-bearing Redis authority in the October 6-authored changes; allocation reduced shared financial-row contention; FP2 and quality probes improved the evidence and selection feeding the provider window. Evaluator changes determined which of these mechanisms a valid run actually measures. A new main-based freeze will already contain these historical improvements: study their mechanisms and remaining costs rather than resubmit them as though the baseline were August's code.

This is a research reading order, not a ranking of measured score gains.

## What the simulator actually measures

The canonical workload is 1,800 providers, 200 client identities, 80 arrivals/minute, quality window 2, four exchange hosts, four fleet shards, and a 180-second measured window, with provider impairment. The authenticated same-round policy and artifacts are authoritative; development stress profiles and old reports are not interchangeable with it (`server/connect/sim-latency/README.md:19`).

The owner states that practical DeviceLocal deployment uses a **32 MiB memory budget**, but this competition **does not enforce that DeviceLocal budget**. That practical sizing/admission context is distinct from the competition's container/resource limits and its synthetic per-provider flow caps. Do not import a 32 MiB per-device acceptance gate into the competition.

The principal data path is:

```text
fake-site HTTP crawl, using a warmed client identity and HTTP connection pool
  -> SDK SimClient's gVisor Tun
  -> RemoteUserNatMultiClient / selected provider / contract-backed Transfer
  -> explicit H1 platform transport
  -> server Connect handler -> resident forwarding + contract authorization
  -> local exchange hop if the destination lives on another simulated host
  -> SDK SimProvider -> RemoteUserNatProvider -> LocalUserNat -> fake origin
  <- provider return path, Transfer recovery, tunnel TCP, complete HTTP body

supporting path: FindProviders2 <- Redis score publication <- reliability /
                performance fixture and periodic UpdateClientScores
control path:   out-of-band contract creation / close and their backing stores
```

The fake site is not a direct shortcut around the provider: `sdk/sim_device.go:488` dials through the Tun; provider composition is at `sdk/sim_device.go:90`. Both simulation endpoints explicitly select H1 (`sdk/sim_device.go:214`, `sdk/sim_device.go:438`). The simulated exchange disables H3 and DNS/UDP listeners (`server/connect/sim-latency/services.go:123`). H1 is a transport family here: newer compatible main endpoints can negotiate H1+ within it, but that does not retroactively add H1+ to epoch 0.

The fixed quality profile is important. A fake site's ephemeral HTTP port could otherwise select the speed window while readiness inspected quality. `server/connect/sim-latency/client.go:725` fixes both active profile and quality-window limits when calibration requests size 2. `server/connect/sim-latency/client.go:749` sizes the HTTP idle/per-host pool to four times the crawl connection count, preserving the six-lane crawl cohort; warmup requires a complete concurrent cohort, not one successful request (`server/connect/sim-latency/client.go:787`). These HTTP lanes are not the optional Transfer logical lanes discussed below.

Idle resident forwards expire after five seconds in the simulator, specifically to keep construction/contract validation in measured traffic (`server/connect/sim-latency/services.go:99`). On newer main, authorization is also checked before offers to an already-live forward (`server/connect/resident.go:4405`). The service's ten-second pipeline refreshes location reliability and restores prewarmed performance, then calls `UpdateClientScores`; it does not run the general taskworker or the complete production URL-prober/settlement fleet (`server/connect/sim-latency/services.go:387`).

## 1. Connect packet batching: preserve bursts across the data plane

### Separate the batching boundaries

The useful question is not "is batching enabled?" but "which repeated operation does this batch eliminate, and who owns every packet when it returns?" These current bounds are independent; they are not one end-to-end batch-size setting.

| Boundary | Current shape / bound | Main role |
| --- | --- | --- |
| SDK native packet bridge | Up to 64 length-prefixed packets and 96 KiB encoded bytes | Amortize a native/Go crossing; reject malformed input before sending |
| Connect exact-flow group | Default 64 packets / 96 KiB per ownership transaction | Parse/group once, enter provider/flow admission as a group |
| Provider return logical group | Up to 16 frames / 24 KiB before carrier-safe splitting | Keep one ordered group admission while Transfer advances bounded chunks |
| Conservative Transfer Pack | At most two ready frames / one `DefaultMtu` of message bytes, except an oversized first frame advances alone | Preserve mixed/H3-compatible packet sizing |
| H1-only Transfer Pack | Up to 16 frames / 3 KiB; established contract-free envelope can use three `DefaultMtu` packets | Combine ready small packets without repeated Pack/ACK overhead |
| H1 carrier writer | Up to 32 already-ready messages, stopping ordinary drain at 12 KiB | Amortize carrier framing and physical writes without an accumulation timer |
| NAT socket writer / receive callback | Separate ready-drain/callback bounds, not the Pack limit | Reduce socket calls, scheduling, and callback overhead |

Sources: `sdk/device_local.go:3885`, `sdk/device_local.go:5216`, `connect/ip_remote_multi_client.go:385`, `connect/ip.go:8910`, `connect/transfer.go:1312`, `connect/transport.go:61`, `connect/ip.go:5734`, and `connect/transfer.go:14260`. A table entry is a current code bound, not evidence that every batch fills to it.

### August 18–25: carrier-aware Pack formation and cheaper encoding

Some foundations predate this research window: pooled hand-written protobuf encoding was already present before August 13, as were basic packet batching and batched receive delivery. Do not attribute their original invention to the August 18 checkpoint. The encoder is nevertheless essential context: it sizes and writes a Pack/TransferFrame directly into a pooled buffer without allocating an intermediate protobuf object graph; output must remain wire-compatible with generated protobuf, including presence rules (`connect/frame_protobuf.go:3`, `connect/frame_protobuf.go:326`).

`connect:be7f1602` (August 18) tightened the ordinary coalescer's byte bound from 3 KiB to one `DefaultMtu` so encrypted packets remain eligible for the bounded H3 packet lane. It also added compact-contract recovery fields to the ACK codec. This illustrates a cross-carrier tradeoff: a universally larger batch can push traffic onto a less suitable lane or exceed an envelope; improving H1 requires identifying H1 rather than relaxing every carrier's limit.

`connect:bb9319b4` (August 25) then introduced H1-specific larger logical chunks and already-ready drains. A logical group is admitted once, retains order and routing ownership, and advances through carrier-safe wire Packs. Its chunk limits are pinned when execution begins so later carrier changes cannot invalidate completion accounting. An established contract-free shape can fit more packet payload, but only after proving the entire remaining group can keep that shape; opening/rotation still needs space for contract metadata (`connect/transfer.go:1114`, `connect/transfer.go:3316`). Independently queued compatible Packs can also coalesce, so a scalar producer can benefit from this layer. Neither mechanism waits for a future packet to arrive.

A larger wire Pack still represents multiple original owners. August 25 kept the common two completion records inline and used a small bounded overflow pool for the H1 tail instead of enlarging every long-lived send item. ACK, first-write, NoAck, failure, and cancellation dispositions must reach the correct original records exactly once. A logical group's success requires every materialized chunk; rejected or unmaterialized tails must be returned (`connect/transfer.go:303`, `connect/transfer.go:405`, `connect/transfer.go:516`, `connect/transfer.go:3382`). Tests explicitly cover sixteen-way ready drains, full-group completion, and partial disposal: `connect/transfer_group_test.go:1031`, `connect/transfer_group_test.go:387`, and `connect/transfer_group_test.go:478`.

The same commit moved decoded ACK protobuf views, IDs, and tag storage into a reusable synchronous owner. Its historical source comment reports eliminating 240 bytes / five allocations per received ACK at the cost of increasing each bounded cached owner; that is a documented allocation result, not a sim-latency speedup. The semantic ACK is copied before that owner returns to the pool (`connect/frame_protobuf.go:791`, `connect/frame_protobuf.go:1519`, `connect/frame_protobuf_test.go:1512`). Codec equivalence and encrypted-envelope tests are critical controls when optimizing this layer (`connect/frame_protobuf_test.go:190`, `connect/frame_protobuf_test.go:919`).

### Carry groups through packet parsing, NAT, and provider returns

Exact-flow groups use the directional IP five-tuple, including IP version; unrelated flows must not accidentally share ordering or custody. The group owns its packet-slice metadata and canonical path. `connect:2db4f81e` (September 21) stopped cloning a path for every packet appended to an existing group, used a stack-local reversed path for committed receive lookups, and bypassed legacy protobuf wrappers on raw provider-packet receive. The uncommon retained fallback still obtains owned state (`connect/ip.go:272`, `connect/ip.go:331`, `connect/ip_packet_memory_regression_test.go:21`, `connect/ip_packet_memory_regression_test.go:54`, `connect/ip_packet_memory_regression_test.go:91`). These improvements reduce repeated work without changing grouping or malformed/legacy packet behavior.

At NAT admission, `SendPacketsWithTimeout` transfers the whole list with one channel operation or leaves the entire list with its caller. The public `SendPacketBatch` instead consumes all packet buffers, returning rejected ones itself; its outer input slice is borrowed only during the call. August 25 fixed the asynchronous local-NAT handoff to clone slice metadata rather than retain the caller's reusable list (`connect/ip.go:211`, `connect/ip.go:1061`, `connect/ip.go:1077`). These similar-looking APIs have deliberately different ownership contracts.

Provider return batching is real in the simulator: its `RemoteUserNatProvider` registers the keyed batch callback on LocalUserNat (`connect/ip.go:7861`). A TCP flow snapshots one stable return TransferKey and recovery mode for the drained batch, then the provider forms logical frame groups (`connect/ip.go:5361`, `connect/ip.go:9095`). Batch callbacks are exclusive with scalar callbacks for those packets; borrowed buffers remain valid only through the callback unless shared read-only. Calling both callback forms would duplicate delivery (`connect/ip.go:1319`). The upstream TCP writer separately drains ready payloads into `net.Buffers`, with progress-bounded writes and release of every buffer/reservation afterward (`connect/ip.go:5734`). Socket-write batching and receive callback coalescing are existing machinery that the period's ownership, memory, and recovery changes hardened, not new August 25 inventions.

### October 10: a blocked group must not hide ready work

`connect:ec99aa73` gives every unrelated already-read native-batch group a zero-wait offer before waiting on a refused group. Later pieces of the same flow cannot overtake their pending head. A continuation keeps its original timeout, packet owners, and policy preparation within the synchronous call; it adds no goroutine, packet copy, or persistent flow cache. Fresh collapse/encryption/queue admission still runs on retry (`connect/ip_packet_group_admission.go:1`).

The batch API counts admitted inputs, not delivered packets. Its result-vector variant preserves exact input-position results, with ordinary same-flow groups admitted as units. Fragment gates and SMTP have explicit ordering/partial-result semantics; pending work is completed at those boundaries (`connect/ip_remote_multi_client.go:6435`, `connect/ip_remote_multi_client.go:6447`, `connect/ip_remote_multi_client.go:6524`). Refusal, finite timeout, and cancellation must return each original owner once. This lets a small ready UDP/request group progress despite another flow's TCP credit stall without pretending the stalled flow delivered.

Applicability is asymmetric. The inspected SimClient uses `ReadBatch` with 64 slots but iterates scalar `SendPacket` calls (`sdk/sim_device.go:421`). It therefore does **not** exercise the whole native multi-flow ready-pass merely because its read API says "Batch." Lower Transfer/H1 coalescing, batched provider returns, and socket writes can still operate. Tests isolate cross-flow credit, cancellation, and the fact that a later native read cannot overtake the prior call (`connect/ip_remote_multi_client_batch_credit_hol_test.go:341`, `connect/ip_remote_multi_client_batch_credit_hol_test.go:437`, `connect/ip_remote_multi_client_batch_credit_hol_test.go:494`). H1+ and Framer, below, optimize the next carrier boundary; they neither replace this payload batching nor prove the native bridge submitted a burst.

## 2. Packet-flow contention and ownership

### Keep receiver callbacks nonblocking

A major historical improvement is **no blocking on shared receiver functions**. The receive path fans incoming frames out to subscribed callbacks; waiting inside one callback can stall unrelated flows and delay the ACK/control traffic needed to clear the congestion. Receiver callbacks should inspect the frame, perform a bounded admission attempt, transfer or retain ownership explicitly, and return. Socket I/O, contract allocation, database work, sleeps, queue-capacity waits, and lifecycle joins belong to the appropriate downstream owner rather than the shared callback. Short state-lock operations still need bounded work; a zero-timeout channel offer does not help if an indirect helper waits on another resource first. See `connect/transfer.go:4043` and the callback inventory at `connect/receive_callback_policy_test.go:280`.

The August 18–25 receive-policy and reliable-H1 work (`connect:be7f1602`, `connect:01ef4d76`, `connect:de5f75ba`) demonstrates the complementary requirements: shared receivers must keep making progress, and reliable bytes must not disappear after being acknowledged. Use bounded per-flow/per-sequence custody, an explicit admission receipt, and capacity notifications to move waiting into the existing owner loop. The reliable ingress path at `connect/ip_provider_reliable_ingress.go:41` either secures ownership or fails its receipt. The delivery queue at `connect/transfer_receive_delivery_retry.go:73` subscribes before checking capacity, avoiding lost wakeups without creating a timer or goroutine per retry. Cancellation and cleanup must release the same original packet exactly once.

This is a rule for shared receiver callbacks, not a claim that every socket reader or downstream sequence worker can never wait. Carrier-specific handoff policy can apply bounded backpressure at the appropriate ownership boundary. Intentional completion backpressure must also occur outside shared sequence-map locks (`connect/transfer.go:5932`). The architectural goal is to keep one slow destination from occupying another destination's receive/admission progress, rather than replace blocking with silent drops or unbounded goroutines.

Concrete regression examples are `connect/transfer_callback_backpressure_test.go:345` (blocked packet handoff cannot stall an unrelated source), `connect/transfer_callback_backpressure_test.go:451` (ACK handoff isolation), and `connect/transfer_callback_backpressure_test.go:21` (close-callback backpressure stays destination-local). The structural guard at `connect/receive_callback_policy_test.go:190` rejects obvious direct waits, blocking send APIs, nonzero-timeout callback handoffs, and channel sends without a default case; indirect helper behavior still requires call-path review. These are useful templates for evaluating a performance change that moves work out of a receiver.

### Isolate flows and preserve bounded ownership

The August low-bar work (`connect:be7f1602`, August 18; `2b1a5b67`, August 19) and August 25 H1 work (`bb9319b4`, `b2ae906f`, `01ef4d76`, `de5f75ba`) attacked several distinct sources of shared-flow delay: pre-sequence admission, per-flow scheduling, logical ordering lanes, callback backpressure, and ACK feedback. They should not be collapsed into a claim that every flow now has its own physical connection.

The current pre-sequence scheduler holds FIFO order within an exact flow and can select active flows round-robin. One valid flow may consume at most capacity−1 admission slots when capacity permits, leaving a slot for newly active work. The complete queued working set remains bounded, including work drained out of the channel into the scheduler (`connect/transfer_send_scheduler.go:25`, `connect/transfer_send_scheduler.go:121`). Bounded logical lanes hash five-tuples into at most eight data lanes, with lane 0 retained for legacy/control traffic; their extra queue capacity is shared, not multiplied by lane count (`connect/transfer_logical_lane.go:3`).

Activation matters: general `LogicalDataLaneCount` remains zero by default (`connect/transfer.go:992`). Explicit mobile H1 enabled bounded lanes in `sdk:e2e50aa7` (August 25), but the simulator does not instantiate the full mobile DeviceLocal policy. Likewise the dedicated H1 ACK-priority channel is optional and defaults to absent (`connect/transport.go:541`). Receivers understanding a capability is not proof a measured sender uses it.

Reliable H1 handoffs were made lossless under bounded backpressure. A reliable message must be retained or refused at an ownership boundary that can retry; it must not be acknowledged and then silently discarded by a downstream callback. Later reliable-ingress work, including `connect:1f8ac317` (September 27) and `10c5bee3` (October 2), preserved progress and custody while provider/NAT admission was pending. Current receipt-based admission separates securing the bytes from later delivery, with capacity notifications and bounded retries (`connect/ip_provider_reliable_ingress.go:41`, `connect/transfer_receive_delivery_retry.go:73`).

On the relay, `server:2425b71e` (September 15) made forwarding shards lazy. Destination-stable queues move slow forward construction and backpressure off the shared receive callback; only active shards get queues/workers (`server/connect/resident.go:3924`, `server/connect/resident.go:3989`, `server/connect/resident.go:4365`). This is especially relevant at fleet scale, where eager per-resident workers and buffers multiply even for quiet residents. `fb1d1eb7` (September 29) stopped idle forward lookup churn and bounded payload lifetime; `2f361252` (September 30) removed unused-forward allocations. October 5's `14355496` and `a25d02b7` tightened idle renewal and deadline admission: refused offers must not keep a full/stalled destination alive (`server/connect/resident.go:4506`).

`connect:ec99aa73` (October 10) added a ready-first pass over native packet batches: unrelated already-read flows get a zero-wait offer before the caller waits on a blocked group. Same-flow groups cannot overtake a blocked predecessor; continuations retain the original deadline and ownership, no new goroutine or copied packet is introduced, and SMTP/fragment ordering boundaries remain respected (`connect/ip_packet_group_admission.go:1`). Cached policy preparation is not permission to skip fresh collapse, encryption, or queue admission on retry.

There is an important measured-path limit: the inspected SimClient reads a batch from its Tun but then calls `SendPacket` sequentially (`sdk/sim_device.go:421`). It does not submit that entire batch through the new multi-flow batch API. Thus this ready-first improvement is a native-path reference, not proven to be exercised as a multi-flow batch by the official bridge. Shared scalar send/admission machinery can still matter. Tests separating these cases include `connect/ip_remote_multi_client_batch_credit_hol_test.go:341`, `connect/ip_remote_multi_client_batch_credit_hol_test.go:437`, and `connect/ip_remote_multi_client_batch_credit_hol_test.go:494`.

## 3. H1, H1+, and framer optimizations

`server:2320a55b` and `connect:bb9319b4` (August 25) increased batching of messages already ready to write. This amortizes framing/write overhead without waiting to accumulate a batch, so sparse traffic need not pay a new batching timer. Current client-side limits drain up to 32 messages or the ordinary-data byte threshold; an optional ACK-priority lane gets a bounded quantum before ready ordinary work gets a turn (`connect/transport.go:61`). The distinction between application batch size, protocol message size, and scratch size must survive tuning.

`connect:7ca82cf8` and `server:4bf49d5d` (September 22) optimized singleton framing as well as multi-message batches. `Framer.WriteBatchWithStorage` can encode a singleton into bounded caller-owned scratch and issue one write; an undersized/no-storage singleton retains the legacy split-write fallback. This is not equivalent to simply routing every singleton through allocating `WriteBatch` (`connect/message_framer.go:184`). The exchange's reusable framing/writev storage and singleton dispatch are at `server/connect/resident.go:2274` and `server/connect/resident.go:2297`.

The same day's `connect:af70de9b` added bounded uint32 FramerXl; `a526ca31` used an unretained temporary buffer for larger XL frames. `fd50ddb6` implemented authenticated native H1+ upgrades; `adf7bb41` enabled H1+ by default on September 23. The custom carrier preserves message boundaries over the upgraded stream and uses the same bounded ready-batch discipline, with a fresh WebSocket fallback when negotiation does not succeed. It is not H3, HTTP/2, or an exemption from authentication. Current negotiation defaults are `connect/transport.go:750` and `server/connect/transport.go:462`; framed ready writes are `connect/transport_h1plus.go:8`.

`connect/framed_message_conn.go:32` documents lazy 16 KiB writer scratch and non-retention of larger XL temporaries. `connect:7bd6994d` (September 23) refined short-H1 dispatch and service-rate provenance. Deadline ownership and liveness were tightened by `8bba0bd1` (September 23), `f6366660` (September 24), and `d82db9e0` (September 25): a failed deadline installation, blocked writer, heartbeat, cancellation, and peer EOF need honest route withdrawal and owned cleanup, not a falsely live carrier.

Buffer reuse must include releasing references, not only returning bytes to a pool. `server:a58dd054` (October 3) cleared completed exchange-batch backing references; `e98735d1` (October 5) cleared writev scratch references even on failed/partial writes. See `server/connect/resident.go:1517`, `server/connect/resident.go:2348`, and `server/connect/resident.go:2694`. A returned pooled buffer still referenced by a long-lived batch can distort retention and complicate custody. Current H1+ liveness controls are in `connect/transport_h1plus_liveness_test.go:279` and `connect/transport_h1plus_liveness_test.go:386`; exchange framing/storage and failed-write ownership are covered by `server/connect/resident_framer_storage_test.go` and `server/connect/resident_writev_retention_test.go`.

For the planned main-based epoch, this is a particularly useful historical example: H1+ and the framer optimizations are already part of the baseline architecture, and explicit H1 permits H1+ negotiation when both endpoints support it. Record the selected carrier rather than assuming WebSocket from the mode name. Only the older epoch-0 checkpoint predates this work.

### Recorded evidence and rejected alternatives

The repository's September 22 production-helper report gives concrete evidence, with an appropriately narrow boundary: real localhost TLS on Apple M4 Pro, Go 1.26.7, `GOMAXPROCS=3`, continuous 1,200-byte packets, identical eleven-message ready batches and 16 KiB scratch, handshake/warmup excluded. Ten fresh-process paired blocks alternated mode order; all 60 observations passed payload/order/boundary verification with the same TLS writes per packet (`connect/H1PLUS.md:376`). The report records these paired medians and 95% bootstrap intervals:

| Direction | H1+ throughput change versus WebSocket | Process CPU reduction |
| --- | --- | --- |
| Upload | +32.35% [32.01%, 43.04%] | 24.35% [23.40%, 30.90%] |
| Download | +18.68% [13.73%, 23.20%] | 16.78% [11.97%, 20.86%] |
| Duplex aggregate | +36.31% [32.50%, 37.71%] | 22.56% [20.93%, 22.78%] |

Allocations per packet fell from 3 / 2 / 2.5 to 1 / 1 / 1 in those directions. These are recorded carrier-efficiency results, not sim-latency score improvements, public-Internet throughput, application TTFB, or energy measurements (`connect/H1PLUS.md:393`).

The independent singleton Framer investigation reports 1,200-byte TLS throughput from 2,378.50 to 4,795.79 Mb/s, a paired +101.65% [98.45%, 104.71%], while halving TLS writes and reducing CPU by 49.56%; ready-batch controls were statistically neutral. Crucially, a 12 KiB singleton got slower on a zero-cost memory writer because full copying replaced half copying. A reusable read-header optimization removed an allocation but regressed combined-carrier upload and was not retained (`connect/H1PLUS.md:741`). The lesson is to measure the relevant transport and preserve neutral/adverse controls, not to assume fewer allocations, fewer writes, or more copying is universally better.

## 4. Windows, pacing, recovery, and connection readiness

Window limits, delivery rates, and recovery clocks are coupled. A larger queue can create more residence time and retries instead of useful throughput; a smaller queue can starve a long-RTT flow. September's changes made those relationships explicit.

### Dynamic window resizing: removing a ceiling on gigabit throughput

The owner identifies **window resizing as a key change that enabled gigabit speed in practice**. It deserves its own architectural example alongside batching and H1+: making packets cheaper cannot fill a fast path if the sender is allowed too few outstanding bytes. This is the Transfer send/receive byte window, not the two-provider quality window or the HTTP crawl connection count.

The governing relationship is the bandwidth-delay product: useful bytes in flight must cover approximately `desired goodput × feedback round trip`. At 1 Gbit/s, 100 ms requires at least 12.5 MB (11.92 MiB) of payload in flight, and 200 ms requires 25 MB (23.84 MiB), before framing and feedback overhead. A fixed 2 MiB payload window on a 100 ms feedback loop permits only about 168 Mbit/s in the idealized window-bound case. Faster encoding or a larger carrier buffer cannot remove that upstream ceiling.

The historical defect was that memory-scaled constants stopped growing at the reference device size: a large provider could inherit a small device's window even when it had ample memory. The September 14 series (`connect:38881fea`, `connect:36f79973`) replaced that fixed ceiling with delivery-sized resizing. The sender starts with a conservative 320 KiB allowance, learns from actual delivered bytes and round-trip evidence, and applies a two-round-trip growth scale. The transfer direction draws a real share of its attached budget rather than a capped scaling of a constant; receive advertisements and memory admission provide independent bounds. The 1 Gbit/s goodput target is converted into framed-byte sizing using the recorded goodput factor. See `connect/transfer.go:680`, `connect/transfer.go:697`, `connect/transfer.go:705`, `connect/transfer.go:715`, `connect/transfer.go:753`, and the estimator at `connect/transfer.go:11534`.

Resizing must reach the whole chain. A larger Transfer window achieves little if the receiver hold, carrier flow-control window, tunnel TCP buffers, or shared service pacing still binds below it. Conversely, multiplying a large window by every sequence would turn throughput into unbounded memory demand. Current settings derive growth from the attached shared budget and retain constant-window behavior when no budget exists (`connect/transfer.go:795`, `connect/transfer.go:848`). Ordinary feedback can grow the learned allowance; an explicit quality remeasurement authorizes a reduction, while hard memory/receiver ceilings and pacing continue to apply (`connect/transfer.go:11534`). The practical DeviceLocal 32 MiB budget therefore constrains a different operating point from this competition, which does not enforce that device budget.

The retained research provides a useful before/after control. `connect/THROUGHPUTFIX.md:10563` records seven alternating paired repetitions of a channel-based Transfer fixture. At a 64 MiB budget and 16 KiB payload, the fixed-window arm versus resized arm measured median goodput of 71 versus 190 Mbit/s at 200 ms, and 34 versus 88 Mbit/s at 400 ms; median paired ratios were 2.92× and 2.42×. These are measurements of the Transfer rule, not the complete tunnel or a gigabit result. The owner's practical gigabit attribution is recorded separately above. That separation lets competitors learn from the mechanism and measured controls without mistaking a configured 1 Gbit/s target for a measured sim-latency score.

Useful reproduction and regression anchors are `connect/transfer_throughput_chain_test.go:137` (design-point measurement), `connect/transfer_throughput_chain_test.go:221` (budget/share sweep), `connect/transfer_window_clamped_fixture_test.go:61` (learned window survives a memory clamp), and `connect/transfer_window_pacing_resize_test.go:12` (resized samples preserve first-byte timing and reordering). The research lesson is to identify the binding window, verify that growth follows real delivery, and test the receiver, pacing, memory clamp, and recovery together. This applies to request completion tails as well as sustained bulk throughput.

### ACK/control batching must shorten feedback, not hide it

ACK compression is separate from packet batching. The receiver keeps cumulative progress, selective evidence, and missing-contract requests in distinct bounded state; a capacity-one wake signal coalesces notifications instead of allocating a new notification per packet (`connect/transfer_ack_compression.go:19`). September's pacing/ACK work, including `connect:d7767627` (September 15), `98fb1c50` (September 16), and `a88fcefa` (September 20), bounded response work and aligned feedback with recovery/delivery evidence. Current responses contain at most 32 individually framed ACKs under an 8 KiB response budget, with selective overflow carried to a later response; they are not a new "32-ACK Pack" (`connect/transfer.go:14148`).

Sparse and recovery traffic cannot simply wait for a full compression interval. The current receive owner sends an idle sequence's first cumulative ACK promptly, can publish a bounded quiet-burst head early, and restores only unwritten feedback after a local route-write refusal. A reused timer and existing bounded compressor handle retries; no unbounded ACK queue is added (`connect/transfer.go:15100`, `connect/transfer.go:15241`). This matters because feedback releases resend/receive capacity and gates the next burst. Counting queue admission as delivery, replaying a stale cumulative head, or losing an ACK after local write refusal can turn a throughput optimization into a long-tail stall.

`connect:d90dd24b` (September 30) added direct publication of accepted feedback into constructor-owned ACK state; `59864c2b` (October 3) removed the now-unused production ACK channel and worker. Validation/coalescing occurs under short owned critical sections, while retained-item mutation remains with the sequence owner. Accepted feedback is visible to lifetime checks before an unrelated worker's scheduling delay can expire its bytes. Explicit legacy/test sequences can still use the old queued path (`connect/transfer.go:7534`, `connect/transfer.go:7620`). Tests preserve finite ACK lifetime, immutable identity, and joined shutdown rather than merely measuring a smaller channel count (`connect/transfer_ack_handoff_lifetime_test.go:69`, `connect/transfer_ack_handoff_lifetime_test.go:286`).

Inner TCP ACKs are a different layer again. August 25's `connect:bb9319b4` let an established pure TCP ACK update the monotonic ACK/window state directly rather than allocate and queue a `TcpSendItem` behind upload payload. A pre-handshake ACK, payload-bearing packet, SYN, FIN, or RST retains the ordered path; a direct window advance wakes the socket reader (`connect/ip.go:4773`, `connect/ip.go:5257`). An optional H1 ACK-priority carrier queue must also give ordinary packets turns: those ordinary packets can themselves carry inner TCP ACKs. Prioritizing outer Transfer ACKs without this fairness can starve the very application flow they support.

### Windows, physical-write evidence, and recovery

`connect:36f79973` (September 14) shipped delivery-sized windows by default after the `38881fea` work. A budgeted sender derives its window from measured delivery and round trip, with receiver-advertised hold capacity, shared byte budget, and a conservative opening allowance. The rule's scale is two delivery round trips, and its 1 Gbit/s target is a sizing parameter, not an achieved benchmark result (`connect/transfer.go:697`, `connect/transfer.go:735`, `connect/transfer.go:795`). An unbudgeted process retains the constant-window behavior; enabling the switch alone is not enough (`connect/transfer.go:844`). The simulator does not explicitly install a mobile process-memory target, so do not assume a mobile window policy is active in its default process.

`d654f826`, `d7767627`, and `59c4b128` (September 15), followed by `98fb1c50`, `76e9eb72`, and `85418859` (September 16–17), paced H1 bursts and corrected service/rate evidence across drains, shared-window activity, delayed ACKs, retries, and provider ACK admission. Receiver ACK timing and actual physical writes matter; queue admission is not delivery, a compressed ACK burst is not unlimited path capacity, and recovery traffic must not corrupt the estimator. `8d42fbdc` (September 18) required fresh RTT evidence after recovery pacing. October 2's `332c0e30` specifically protected recovery under H1 pacing admission.

Recovery also became more lane-aware. `connect:1de7604a` (September 11) deferred resends while a live carrying lane was still draining; `05f7c016` and `52b423c1` (September 17) handled carrier-change successors and bounded recovery work. Selective ACK evidence must be invalidated appropriately after carrier replacement. Do not mistake every research mechanism for a shipping default: reliable-delivery admission bounds, deviation timers, and proven-lane recovery remain disabled in the current default settings (`connect/transfer.go:951`).

`connect:b35e03fd` (August 26) repaired poisoned H1 exit recovery; `635e7b64` (August 27) routed fresh flows using measured provider quality while preserving established-flow identity. `dd2557b7` (September 24) woke connection setup when provider/cipher readiness changed instead of relying only on polling. TLS replacement fixes `604ea7f5`, `c98eb715`, and `b9ff27f5` (September 23–24) preserved contract-control readability, handshake generation, and recovery after a failed replacement. These affect setup/renewal tails when encryption is in use; they are not evidence that the loopback HTTP origin itself performs public TLS handshakes.

Relevant navigation: `connect/transfer_encrypt.go`, `connect/ip_remote_multi_client_affinity_performance.go`, `connect/transfer_required_cipher_wakeup_test.go`, and `connect/transfer_window_pacing_h1_admission_recovery_test.go`. Readiness must mean usable authorized delivery, not merely a socket existing.

## 5. Memory budgets, NAT flow limits, and provider return paths

Deployment context supplied by the owner: DeviceLocal has a 32 MiB memory budget in practice; the competition does not enforce it. Treat the mobile work below as historical examples of improving throughput/latency under tight owner budgets, not as a mandate to impose that budget on simulated clients. A DeviceLocal sizing/admission target is also not automatically a hard 32 MiB RSS or cgroup limit. The evaluator's separate resource gate still applies.

## 6. SDK integration: select the right Connect path and own its lifetime

SDK is the adapter between a device/native packet source and Connect, not an alternative transport implementation. Its changes matter when they select a Connect policy, remove native-boundary overhead, make memory genuinely per-device, or fix readiness and teardown.

`sdk:f71f5f0c` (August 18) bounded encoded packet bursts at 64 packets / 96 KiB and validated a complete burst before emitting callbacks or sending its first packet. ## 7. Contract allocation: reduce duplicate demand and shared financial contention

Authorization and allocation are separate costs. A faster boolean resident lookup does not eliminate the client's need to acquire a contract, create a companion reply contract, renew it, or settle usage.

`connect:24780e78` (September 27) coalesced identical pending creates within the exact contract-queue generation. A late result must be delivered only to the generation that requested it, not a replacement queue. Current registration and release are at `connect/transfer_contract_manager.go:1574` and `connect/transfer_contract_manager.go:2102`. This avoids duplicate out-of-band allocation when a sequence retries while its earlier create is still pending, without sharing ownership across unrelated lanes or generations.

`connect:ee4f26c4` (October 11) stopped requesting a large successor immediately whenever an opening contract was taken. The successor becomes due when consumption reaches the configured minimum and projected remaining room above the announcement floor would run out within the lead time; room already at the floor is due regardless of rate. Defaults are a 30-second lead and 64 KiB minimum, capped by half the contract for the minimum-use decision. An already-queued successor counts as requested, and a queued opening is taken before requesting another opening. No-ACK reservation progress explicitly wakes the owner so that fast-path traffic cannot fill a contract without triggering prefetch (`connect/transfer.go:982`, `connect/transfer.go:9849`, `connect/transfer.go:9880`, `connect/transfer.go:9906`). Same-network zero-escrow peers retain eager behavior; a zero lead restores the old policy.

The commit describes main observations of unused contracts and escrow, but those are production diagnostic observations, not sim-latency A/B evidence. Its causal mechanism is nevertheless especially relevant to persistent quality pings and short crawls: they need not reserve an unused next-ramp contract. The controls also preserve timely successors for sustained transfers. See `connect/transfer_contract_successor_test.go:170`, `connect/transfer_contract_successor_test.go:216`, `connect/transfer_contract_successor_test.go:247`, and `connect/transfer_contract_successor_test.go:311`.

On the server, October 2's `6a6f48b3` queued same-payer admission before acquiring a database connection. Waiting for one payer's financial lock should not occupy the entire shared connection pool. The queue is process-local scheduling only: durable financial checks and inter-process fences remain authoritative, and entries disappear when their holders/waiters leave (`server/model/subscription_payer_admission.go:15`).

`server:b3e96e42` then moved reservation admission from shared PostgreSQL financial rows to bounded Redis coordination; `75b40973` removed the retired policy lookup. Current ordinary Redis admission skips that legacy payer gate (`server/model/subscription_payer_admission.go:80`, `server/model/subscription_redis_admission.go:109`). A request keeps a stable reservation identity, uses same-slot keys and bounded grant selection, and performs monetary arithmetic without Lua floating-point rounding (`server/model/subscription_redis_admission.go:119`). Follow-ons `89b295d7`, `164e42a6`, `4aaf4402`, and `34725fe6` on October 3 dealt with compensation, SQL-fenced recovery of retained reservations, selection bounds, and shrinking a contract to available balance.

This intentionally changes the coordination tradeoff; it is not a claim that Redis makes financial state strictly serializable. The source explicitly documents possible over-admission after Redis loss/stale concurrent debit and temporary under-admission from retained tokens. Durable usage and debit authority remain separate (`server/model/subscription_redis_admission.go:18`). Correctness requires stable identities, exact compensation ownership, and reconciliation, not merely replacing a SQL lock with a counter.

`server:c56f9557` (October 2) moved current-contract debit batches outside request locks; `307170aa` (October 3) deferred legacy settlement through durable per-contract intents. These reduce the coupling between close requests and shared financial work, while retaining durable obligations. They belong in the contention model, but the official simulator's service loop does not automatically execute every production settlement worker. Do not infer an evaluation improvement from reduced production worker backlog alone.

## 8. Resident authorization: bound work, share it, then remove packet-side SQL

### October 5: bounded bidirectional existence and read coalescing

`server:4580d931` added on-use expiry sweeps so a long-lived resident does not retain every provider pair it ever encountered. `server:3a13e513` introduced strict contract deadlines and relay leases; `server:ec8a66b0` composed the final Redis-only packet policy and retired packet-triggered fallback work. This is the architectural break:

- Packet readers use an unordered client pair and a same-slot Redis count/member-deadline projection. The index uses unique accepted measurements in an eight-hour window. Stale/missing observations are not fabricated perfect history (`server/model/egress_index.go:20`, `server/model/egress_index.go:107`; `server/model/provider_eligibility.go:12`).

`server:9d890f6d` (September 29) corrected the rolling quota to count accepted measured successes plus failures. The ten-run/four-hour target is scheduling coverage, not an extra ten-success admission gate. Attempts, claims, setup-only turns, duplicate publications, and accepted measured outcomes are distinct. Renewal scheduling (`348742e5`, October 3) acts before the oldest qualifying evidence expires, while security revalidation remains independently due (`server/model/provider_url_probe_due.go:39`; `server/FP2FIX.md:650`). These repairs target fairness, freshness, and database/prober work, not merely a headline completion rate.

Finally, `server:0ec00072` (October 10) made rank-mode Online draw from the Online source, and `d0bbc395` (October 13) excluded repeatedly measured providers with no URL success from fallback membership. The latter preserves benefit of doubt for fewer than two measured runs and a country common-mode guard when the probe itself appears to fail. It does not block probing, explicit-ID access, or force-minimum diagnostics, so a first successful measurement can restore membership (`server/FP2FIX.md:130`, `server/FP2FIX.md:259`). Treat this as a changed selection contract, not a free acceleration: excluding poor exits can alter pool sizes and the G4 gate.

Read the accompanying controls in `server/model/network_client_score_native_cost_test.go`, `server/model/network_client_score_native_availability_test.go`, `server/model/fp2_gate_test.go`, and `server/model/provider_url_probe_due_test.go`. ## 12. PERFVAR: weeks of diagnosis, not one benchmark run

### Read the campaign history as an evidence trail

The PERFVAR work ran as a succession of investigations over **weeks**. The checked-in record spans August's same-host low-bar/batching work, September's flight/window/ownership campaigns, and October's loaded-H1 and physical-memory investigations through October 13. This is not a claim that one replicate ran continuously for weeks. Individual runs, fresh-process cohorts, source-pinned replays, deterministic regressions, rejected candidates, and physical session blocks are different units.

The principal log is `tests/PERFVAR-MEASUREMENTS.md:1`, an append-only privacy-safe ledger, not a directory of raw public packet traces. It records source/dirty-state identities, schema and scenario identities, outcomes, and private artifact fingerprints. The older `server/connect/perfvar/MEASUREMENTS.md:3` contains the August historical baseline and focused comparisons; `server/connect/perfvar/RUN-MAIN.md:3` defines the later campaign contract. This report inspected those checked-in records, not their private raw bundles. The evidence repository was clean at tests `a0de405f9cb1c48f080a599d300c9fa45e45f31a` (October 13). A ledger entry describing a private or rejected candidate is **not** evidence that its patch landed on main; the dated main history above remains the landing authority. Status statements below describe the cited cohort, not an inferred current campaign status.

PERFVAR complements sim-latency rather than supplying its score. It conditions individual packet paths: clean and impaired access, asymmetric rates, 500-ms/1-s regional RTT, loss/queue/MTU changes, one-second outages, dynamic rate collapse, H1/H3/legacy and fast P2P/Auto, upload/download, cold and bandwidth-delay-product-warmed TCP, and UDP latency under concurrent bulk. These cells can isolate a boundary hidden inside a fleet-level page-load percentile (`server/connect/perfvar/PERFVAR.md:135`, `server/connect/perfvar/PERFVAR.md:429`, `server/connect/perfvar/PERFVAR.md:552`). The full matrix is not the official H1-only sim-latency workload. Indeed the harness explicitly leaves sim-latency to its separate evaluator (`server/connect/perfvar/RUN-MAIN.md:13`).

### Deep findings and rejected repairs worth studying

**Batching and host drift, August 25.** A same-binary TLS writer sweep measured ready limits 8/16/32 with seven repetitions per point: 8-to-32 improved full-payload throughput by 12.9% and ACK-sized throughput by 85.2%, without an accumulation timer or extra socket storage. These are recorded saturated-helper results, not crawl-score gains. A separate roughly 20% cross-day slowdown across unrelated packages disappeared in same-session baseline/current/current/baseline isolation; the old source reproduced the slower host state. An attempted 10-ms H1 wait-for-backpressure policy reduced an order-balanced median from 28.90 to 24.00 Mbit/s and was reverted. The lesson is ready-only aggregation plus a sparse-traffic control, not simply bigger queues or fewer flushes (`server/connect/perfvar/MEASUREMENTS.md:1881`, `server/connect/perfvar/MEASUREMENTS.md:1923`).

**Acknowledged bytes cannot remain evictable, September's hold investigation.** In a deliberately inverted-budget fixture, a 0.312-MiB receiver hold faced a 2-MiB peer window, with two routes and one killed mid-transfer. Committed-prefix acknowledgement delivered all 20,000 messages in 3/3 runs with zero evictions of acknowledged items; unconditional eviction completed 0/3 and evicted 793–960 ACKed items, while refusal completed 1/3. This is a mechanism/correctness comparison, not a three-run universal throughput claim (`tests/PERFVAR-MEASUREMENTS.md:4493`). It explains the September 14 main work `connect:609cb1b6` and `38d637c5`: ACK only irrevocably retained progress and commit a safe prefix efficiently. The invariant is directly testable at `connect/transfer_receive_hold_policy_test.go:19`. Merely enlarging a sender window can overrun the peer's actual custody.

**Reliable ingress and inner TCP loss are separate boundaries, September 26.** The source-bound H1 provider-admission comparison found no statistically established speed improvement under its five-process paired decision gate. Its shaped-loss runs showed inner-TCP retransmissions even with zero provider ingress/return-queue drops; the fixture never saturated the repaired ingress boundary. Therefore it could not estimate the performance effect of eliminating an ACK-then-drop bug. Deterministic saturation tests, not a nonbinding broad benchmark, remain the causal evidence for that repair (`tests/PERFVAR-MEASUREMENTS.md:7077`, `connect/ip_provider_reliable_ingress_backpressure_test.go:314`, `connect/ip_provider_reliable_ingress_backpressure_test.go:645`). Nearby UDP work rejected a one-Pack logical-group direct-write candidate after reversed-order H3 controls exposed a regression, even though H1/P2P correctness passed (`tests/PERFVAR-MEASUREMENTS.md:7046`).

**A complete body is not a complete transaction, October 2.** The full static command retained 7 incorrect records out of 360; some H1 downloads had verified every body byte before completion failed. A focused candidate replay received its 1-MiB body by 9.50 seconds but timed out on completion at 102.57 seconds after ACK-owner expiry and many provider resends. That does not establish that the candidate caused the failure. A separate private gVisor PTO guard had a deterministic RED/GREEN reproduction, but mixed full-TUN results and unchanged release dependencies prevented a release-cure claim. Preserve body, completion-return, ACK lifetime, and teardown as separate stages (`tests/PERFVAR-MEASUREMENTS.md:7460`).

**H1 stream delay, pacing, and recovery-owner progress, October 7–10.** An instrumented H1+ replay correlated an exact frame hash from a successful provider write to its matching device read **8.114 seconds later**. Twenty-three reliable bulk frames preceded that small NoAck frame; the evidence supports shared-stream queued-bulk/head-of-line delay in that traced arm, not a mapping of every historical probe to a lost TCP segment (`tests/PERFVAR-MEASUREMENTS.md:7537`). Follow-up tests exposed inconsistent opening-credit serialization/refill versus the congested estimator, and sparse lifetime bytes incorrectly qualifying a 510-B/s service estimate that priced a first bulk reservation at 6.139 seconds. Fixing only one side was insufficient: a focused 17-test pass still failed two of 399 broader tests, including route replacement/recovery progress (`tests/PERFVAR-MEASUREMENTS.md:10302`).

The fixed-16-KiB experiment is especially instructive: first interactive reply age improved from about 9.266 to 0.619 seconds, but bulk slowed; the treatment also reduced startup pacing allowance, so it did not isolate window size alone. It was rejected, not adopted as a latency cure (`tests/PERFVAR-MEASUREMENTS.md:10226`). Another partial-group ownership candidate passed three fresh 33-test sets, yet a separately constructed accepted-RST/new-SYN case still orphaned the later accepted cohort. That missing invariant, not the number of previous green tests, controlled integration (`tests/PERFVAR-MEASUREMENTS.md:10280`). Existing main recovery controls to read alongside these investigations are `connect/transfer_window_pacing_h1_admission_recovery_test.go:16` and `connect/transfer_window_pacing_h1_admission_recovery_test.go:20`; a test's present existence does not retrospectively qualify a private overlay.

October 10's ten-process D/E census retained every scheduled observation, including a calibration-invalid process. Both arms were private overlays, all payloads were correct, and loaded-probe latency/failure outcomes remained mixed; repeating one fixed Run1 was not five independent workload seeds. No statistical win or baseline promotion followed. A separate phase trace conserved 314 offers as 143 accepted, 170 expired, and one late; reader-to-owner handoff stayed below 0.221 ms, so that handoff/deadline accounting was not the observed multi-second delay. The logs narrowed the next causal test to intermediate admission/carrier/receive boundaries, without claiming those boundaries had already been proved responsible (`tests/PERFVAR-MEASUREMENTS.md:10414`, `tests/PERFVAR-MEASUREMENTS.md:10550`).

### Instrument defects are part of the findings

The long campaign also found plausible-looking explanations that did not survive controls:

- **Sample size and noise:** unchanged-source A/A at five repetitions would have called 15 of 17 cells worse under the then-used rule. The ledger explicitly retired those earlier five-run verdicts. More requests inside one run do not create independent source comparisons (`tests/PERFVAR-MEASUREMENTS.md:167`).
- **Wrong operating regime:** a window sweep at 25-ms RTT could not test a bound that only became active above roughly 88 ms. Raising RTT exposed the bandwidth-delay constraint. A max-only lateness gate also rejected slow arms preferentially, motivating separately recorded mean, maximum, and measured RTT-floor checks (`tests/PERFVAR-MEASUREMENTS.md:3585`).
- **The emulator was the bottleneck:** netem's default 1,000-packet queue dropped offered UDP before it reached the provider, while provider socket-drop counters correctly stayed near zero. The campaign measured its queue, not the hypothesized provider ceiling (`tests/PERFVAR-MEASUREMENTS.md:2951`).
- **The observer changed the path:** per-frame sleep granularity capped an intended rate; a deep carrier route absorbed backpressure upstream of the queue under test; global pool occupancy substituted for the specific sender queue. Concurrent test work contaminated a recorded comparison, and an old benchmark-listing process consumed a core during another cohort (`tests/PERFVAR-MEASUREMENTS.md:4073`, `tests/PERFVAR-MEASUREMENTS.md:2307`, `server/connect/perfvar/MEASUREMENTS.md:1923`).
- **An inferred counter was not measured:** the ledger retracted its apparent 28,000-Packs/s send-loop ceiling. That number came from window/period/payload arithmetic; no loop iterations had been counted. Fill slope and achieved throughput were different quantities (`tests/PERFVAR-MEASUREMENTS.md:5241`).
- **A timeout can truncate the experiment:** the older long-transfer exploration stopped at exactly 8 minutes 57 seconds despite continuing packet activity. It was not accepted as throughput evidence; the replacement used context-bound, rate-scaled deadlines and explicit calibration failures (`server/connect/perfvar/MEASUREMENTS.md:27`).

Memory conclusions need the same discipline. September's owner fix lowered a recorded physical runtime peak by 8.2% but still failed that historical profile's absolute gate; later quiet reclaim did not erase the active peak (`tests/PERFVAR-MEASUREMENTS.md:5723`). Later iOS32/Android64 protocols are separate cohorts, not retroactive reinterpretations of the old 24-MiB contract. Physical profile gates and thousands of correlated collector samples are not the sim-latency competition's DeviceLocal limit or independent performance replicates (`tests/PERFVAR-MEASUREMENTS.md:201`). The owner-provided practical 32-MiB DeviceLocal budget remains **unenforced by this competition**.

### Turn a week-long incident into a bounded regression

Use the ledger to choose the mechanism and original counterexample, then freeze the source closure, module resolution, workload/schema, role/direction, carrier, budget, and original deadlines. Establish exact packet/sequence/owner lineage and distinguish admission, physical write, peer receipt, ACK, delivery, and application completion. Convert the failure into a deterministic test with controls for ordering, cancellation, lost heads, carrier replacement, cold opening, and steady bulk; preserve the unchanged RED, not just the candidate GREEN.

Only then compare trace-off independent runs under a matching cohort, with every invalid/failed attempt retained and broader correctness/resource gates intact. Private diagnostic passes, lower allocations, one faster probe, or a successful cleanup are useful evidence but not baseline promotion. This is why the weeks-long PERFVAR history is a research seed: it supplies difficult counterexamples and discriminating tests, not a menu of guaranteed speedups (`server/connect/perfvar/RUN-MAIN.md:65`, `server/connect/perfvar/RUN-MAIN.md:146`).
