# Offline native storage facts

`VerifyReceiptNativeState` verifies raw storage bytes at the receipt collection's
exact native boundary. It first replays `VerifyReceiptFinality`, including archived
transaction/receipt proofs, weighted GRANDPA certificates, header ancestry and the
Frontier commitment. Only that replay's `NativeStateRoot` selects the trie. A v2
certificate may target a later descendant; storage remains bound to the original
collection header. Native and EVM heights are separate domains.

The new API and `LoadReceiptNativeStateWitness` are offline library entry points.
They add no command, RPC client, signer, custody operation, runtime interpretation
or spending permission. Existing receipt/finality APIs and schemas are unchanged.

## Witness and codec

The witness schema is `urnetwork-receipt-native-state-witness-v1`. It binds the
decoded collection, checkpoint and finality proof digests, the native boundary's
number/hash, expected raw reads and raw `StorageProof` node blobs. The codec is
`substrate-blake2-raw-storage-proof-v1`. There is deliberately no supplied root,
runtime version or approval boolean. A read's `null` value means absent; `"0x"`
means a present empty value. Canonical lowercase hex is required for all bytes.

The implementation follows the shared no-extension `NodeCodec` in the pinned
polkadot-sdk commit `cacb4310f20c7cac83eb3ccd8ed5a5ad4212608a`, tree
`d2a88f2922e812acfea1791c6994065c450443a0`: Blake2-256 addresses, packed partial
nibbles, branch bitmaps, SCALE compact lengths, inline children and external
hashed values. LayoutV0 and LayoutV1 use this reader; their write policies differ.
Recognizing either shape does not establish a chain's runtime or state version.

The supported canonical profile refuses trailing node bytes, nonminimal SCALE
lengths, invalid odd-nibble padding, empty branch bitmaps, unsupported headers,
and child references outside 1–32 bytes. These are conservative bounds for
canonical SDK-produced tries, not a promise to accept every permissive decoder
input. Duplicate raw blobs and duplicate requested keys are rejected. Node order
is immaterial; bounded unused blobs are allowed in proof unions and are not
decoded as trie nodes because an external value may contain arbitrary bytes.
Missing hashed nodes or values are incomplete evidence, never proven absence.
The SDK's intrinsic null root authenticates absence without a supplied blob.

`generate_trie_proof` and `CompactProof` are different encodings and must not be
substituted for `Recorder::drain_storage_proof`. Four trivial oracle cases happen
to have identical raw and generated bytes; no verifier can distinguish those
identical representations. The fourteen differing generated proofs are rejected.

## Bounds and ownership

One call admits one native block, 1–32 reads, at most 8,192 distinct proof blobs,
keys up to 1,024 bytes and individual blobs/expected values up to 16 MiB. All
decoded blobs, keys and expected values share a 64 MiB budget. The private file
loader additionally caps JSON at 129 MiB and verifies its exact SHA-256 pin.
Counts and encoded lengths are checked before allocation. Traversal is iterative,
consumes at least one key nibble per child and caches each visited node decode.
Context checks bound work between blobs, reads and traversal steps. A single
bounded hex decode/hash is synchronous; there is no hard real-time guarantee.

Inputs are borrowed immutable values for the call. The result owns its read value
pointers and is returned only after all expected reads agree. No partial report
escapes on cancellation, malformed data or a failed association.

## Independent oracle and qualification boundary

The Rust oracle is frozen at server commit
`a2dd62b54ca5c122bd2f4fb28d9bbb26c6cec2ef`, tree
`40c0eca6b9fc97098ac9d992f71f6e77efd242f7`. It builds actual SDK tries, records
reads, reconstructs `StorageProof::into_memory_db`, replays every read and also
verifies the separate generated-proof encoding. It uses synthetic data only.
Cargo dependencies are locked and the SDK source is physically pinned.

Sol independently ran it offline and repeated the rebuilt binary with identical
output. The 18-vector fixture SHA-256 is
`b875b9eb1aa497233f68bb4cae02b4331320fcaeeaaefbefe867658f2aebaecd`; the nine-file
oracle receipt manifest is
`ba84714e74239278f8f9f68d379b664eaf31dfa8213a9076ff84a50b1495164a` at
`/mnt/data/sn-testnet/qualification/native-storage-proof-oracle-sol-20260929`.
This qualifies the oracle, not the Go implementation. The candidate's Go behavior
and causal controls require separate independent qualification after source freeze.

The first Go candidate, `b0ca782ae80976bc7f7a1312351d79aa7d47ba08`, failed setup in
fourteen of fifteen selected normal roots: its fixture helper compared the
recovery protocol's `sha256:<hex>` digest with this receipt's bare hex checksum.
The original vector bytes matched; no verifier qualification followed. The child
fixture fix uses explicit standard SHA-256 for the bare file checksum and tests
both digest domains plus rejection of a whitespace-only byte change. Production
verifier code is unchanged. Sol's original failed stream is preserved at
`/mnt/data/sn-testnet/qualification/native-storage-proof-verifier-sol-20260929/frozen-b0ca`,
manifest `a296fd109912ee5dd561499f72ae2cb0d9210c39187c1650dd8429211784de06`.

The next candidate, `4ffecfb393833a2878030edfd483ecca9293699a`, passed sixteen
focused and six adjacent roots in both modes, but its `ignore-file-pin` normal
control incorrectly passed: the negative fixture supplied a malformed bare pin,
so syntax validation refused it before byte comparison. That control is invalid;
the candidate remains unqualified. Its raw evidence stays in the sibling
`frozen-4ffe` qualification directory. The next fixture-only child uses a canonical
mismatched pin, requires the byte-comparison error explicitly and tests malformed
syntax separately. Witness association substitutions also use canonical protocol
digests. Production verifier bytes remain unchanged; qualification must be sealed
on the corrected child before integration.

## Remaining launch dependencies

Successful output is an `unapproved_observation` with native header/storage math
verified relative to the still-unapproved checkpoint. Genesis, authority checkpoint,
runtime source/storage decoding, live finality, owner authority window, global
coldkey custody, actual fee reconciliation, enforceable fee exposure and spending
authorization stay false. Earlier receipt histories and null actual fees remain
intact. No `System.Account`, event, nonce, miner, stake, proxy or fee interpretation
is inferred from raw bytes. Child tries and proofs at arbitrary earlier receipt
blocks are outside this initial profile.

A later runtime-aware layer needs independently approved source/compiler/metadata
and storage layout, an approved checkpoint for the intended Snow identity, exact
native block selection and its own causal tests. Raw storage facts alone cannot
enforce the owner-trim mortality window, monopolize all coldkey signing routes or
cap execution-time fees. No live launch blocker is silently marked resolved.
