# Client close (CLIENTCLOSE1)

Owner direction, 2026-10-28:

- "The expiration time of a contract should be 60 minutes. I think the root issue is that we don't have a close message that a client can send the provider to close the sequence now, so each client waits for the provider to close on a read sequence time out. The close message could be automatically generated by server/connect when a client is removed, for any client where there exists an open contract. I think that might help cycle balance faster. We could have a general client_close_model that follows the redis notification of for example stream_model"
- "The resident should also close immediately when the client is removed"
- "server/proxy should also close devices when the client is removed"
- Removal means API removal only: "A disconnected client will unfortunately have to be time outs."

## What happens today

- **Every new contract has a 60-minute deadline**, sealed into the signed contract (`model.DefaultContractExpiration`). Neither client closes a contract when its deadline passes; the deadline only stops new debits.
- **A contract settles on reports** only when both parties have sent a final close (`contractClosesMaySettle`), or when the receiver reports after the sender's final (owner decision B, 2026-10-10). Otherwise the expiry sweep settles it.
- **The receiver never finalizes the contract it is on.** When a receive sequence exits (120 s idle, a gap, cancel, shutdown), it sends finals for the contracts it has moved past. For its current contract it sends only a checkpoint, because the sender may resume it (connect `transfer.go`, ReceiveSequence exit). The sender sends its finals when its send sequence exits after 300 s idle. In the common case the receiver checkpoints at +120 s and the sender finals at +300 s. The receiver's report then comes before the sender's final, so decision B does not apply and the contract waits for the sweep.
- **The sweep cannot keep up with a large payer.** A deadline close takes the payer's grant lock and costs about 30 ms, so one payer's closes run one at a time (`subscription_close_turns.go`, `subscription_close_deadline_batch.go`). The hot proxy network had 15.2M open contracts on 2026-10-28. Its Redis reservations, which have a 24 h lease, filled its grants until the grant spread.
- **Removing a client** (`RemoveNetworkClient`, about 30-70/s on main) writes revocation records and nothing else:
  - its transports close at the next authorization recheck, within 60 s, with code 4005;
  - its resident lives until its idle watcher cancels it, 5 to 20 minutes later;
  - a proxy device for it serves until its 90-minute idle timeout;
  - its contracts wait for the sweep.
  Most removals are hosted window identities that a multi-client retires after `CloseAndWait`, so their sender finals have already gone out.

## Design

### 1. `CloseSequences`, a new connect message from the platform to a client

`TransferCloseSequences = 36`, message `CloseSequences { repeated bytes contract_ids = 1; repeated bytes peer_ids = 2; }`. Only the platform sends it (source `ControlId`), so it needs no contract or peer session. Older clients ignore the unknown type, and their contracts close as they do today.

The client closes each listed contract now:

| Where the contract is | What the client does |
|---|---|
| A live receive sequence has it open but not current | Sends a final with that sequence's counts and drops the contract from the sequence. |
| It is a live receive sequence's current contract | Cancels that sequence and finalizes every contract it holds, including the current one: the other party has finished with it. |
| A live send sequence holds it | Cancels that send sequence; its exit sends finals as it does today. |
| The client no longer holds it | Sends a final of (0, 0). Its counts went out earlier, for example in the checkpoint at sequence exit, and the server turns that checkpoint into a final with the same count. |

For each peer in `peer_ids` (a removed client), the client cancels every receive sequence from that peer (finalizing its current contract too) and every send sequence to it, and drops queued contracts for it.

The handler runs on the control sequence's goroutine, so it hands the work to a worker and returns.

This is the close message the owner asked for, with one change: the platform sends it, not the sender. When the sender's sequence ends, the receiver's sequence has usually exited three minutes earlier, so a message on the sender's own sequence would find nothing to close. The sender's final close report already tells the platform that the sender is done. The platform passes that on (section 3), and the passed-on message also reaches receivers whose sequences have already exited.

### 2. `client_close_model`, Redis keys and keyspace notifications

Modeled on `stream_model` (`{<clientId>}s2_c_hops`). Main enables keyspace event classes `Kg$sx`, so a SET, SADD, DEL or expiry each produces an event.

- **`{<clientId>}c_removed`**, string, 2 h TTL. Set after a removal commits. Every connect and proxy process subscribes to `__keyspace@<db>__:{*}c_removed`.
- **`{<clientId>}c_close`**, a set of pending close items for the client: `c:<contractId>` and `p:<peerId>`. Each add renews a 15-minute TTL. Only the process that hosts the client's resident consumes it, through a per-resident listener registered like the stream hop listener. On each event, and once when the listener registers, it pops up to 1024 items (SPOP, so exactly one consumer takes each item) and sends them as one `CloseSequences`.

Both keys have one hash tag, so each write is a one-slot script. If an event is missed during a resubscribe:

- items in `c_close` wait for the next event for that client or for the listener to register again, and otherwise expire, leaving those contracts to the sweep, as today;
- a missed `c_removed` event is covered by the 60 s authorization recheck for transports and by the idle watchers for residents and devices.

### 3. Settling at the sender's final

**Owner decision, 2026-10-28:** a sender's final that arrives after the receiver's checkpoint settles the contract in the sender's report.
- The rule mirrors decision B (2026-10-10), which covers the opposite order: a receiver checkpoint after the sender's final.
- In the common order the receiver checkpoints at its exit and sends nothing more, so the counts on hand are the ones the sweep would settle with (the mean of the two). The contract now settles about an hour sooner, without waiting for a provider update.
- The guards are the same as decision B's: no outcome, no dispute, expiry not started, and the sender's count not a legacy lower bound.
- The two counts must agree within `AcceptableTransfersByteDifference` (16 MiB) in either direction. Counts that disagree by more are left to the sweep, as before.
- Mechanics: `applyLockedContractCloseReportInTx` reports `contractSenderFinalAfterCheckpoint`, and `settleContractWithOptions` completes the checkpoint as a zero final and settles in the same transaction, as it does for decision B.

**A receiver with no report yet is asked for its final.** When a source final commits (applied, `party == source`, not a checkpoint) and the destination has neither a final nor a checkpoint, a post-commit step adds `c:<contractId>` to the destination's `c_close`. The destination's final then settles the contract on reports.
- Retries and replays (`terminalReplay`, not applied) add nothing.
- A failed Redis write leaves the contract to the sweep.

Both paths settle through the ordinary settlement path, which leaves the grant debit to the debit worker, instead of the sweep's per-payer path. They cover normal clients and retired hosted windows alike.

### 4. API removal

After a removal commits (`deactivateLockedNetworkClientsInTx`, which batch, task, prober and session removals all go through), a post-commit step:

1. sets `{X}c_removed` for each removed client X;
2. reads X's open contracts (`GetOpenContractIdsForSourceOrDestination`, at most 4096 per client), groups them by counterparty P, and adds each contract `c:<contractId>` plus `p:<X>` to P's `c_close`.

Every connect process that sees the `c_removed` event:

- closes X's transports on that process with the typed authorization close, 4005, which is what the lease recheck would send 60 s later;
- if it hosts X's resident, cancels the resident after the transports close. A surviving transport would nominate a new resident within about a second, and nomination does not check `active`.

The counterparties' finals then arrive through section 1. Contracts that X never finalized, for example because it crashed before it was removed, keep only the counterparty's final and settle at the sweep, as today. Settling those early (`ReconcileContractAtDeadline` after a grace period) costs the same per-payer sweep time, just sooner, so it is left as a follow-up.

### 5. Proxy devices

The proxy device manager keeps an index from a client id to the proxy ids of its devices. It subscribes to `{*}c_removed` with `server.SubscribeKeyEvents` and closes the devices of a removed client. On each (re)subscribe it checks the `c_removed` key of each local device's client, because devices have no other prompt backstop. Their idle timeout is 90 minutes.

### What does not change

- A disconnected client that never sends its finals still waits for the deadline and the sweep (owner: time outs).
- The reservation lease stays 24 h. A 60-75 minute lease would expire tokens that PostgreSQL still marks `redis_reserved` on contracts the sweep has not closed yet, and `settle` and `release` of a missing token do nothing, which over-admits the grant (`subscription_redis_admission.go`). Revisit it once settlement keeps up.
- The 60-minute deadline already exists; this design makes it matter less.

## Rollout

1. **Server:** the model, connect, api and taskworker (each runs the close report path), and proxy.
   - Settling at the sender's final (section 3) takes effect with this step.
   - Older clients ignore `CloseSequences`.
   - The cost is one SADD per sender final whose receiver has not reported, and one per removed contract.
2. **The connect library and SDK release.** Providers that update send their finals on request, both for contracts whose receiver had not reported and for removed peers.
3. Watch `urnetwork_redis_contract_reservation_total{operation="reserve-pending",result="skipped"}`, the hot network's open-contract count, and settle versus expiry closes.
